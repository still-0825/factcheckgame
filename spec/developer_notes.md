本ドキュメントでは、本作の仕様書を別のAIモデルやプログラマーに渡し、実際にプログラム（コード）に落とし込む際に**「曖昧になりやすい点」や「開発時に疑問を抱く可能性が高い点」**をゲームプログラマーの視点から先回りして整理・抽出したものです。

これらのポイントを明確にすることで、将来AIモデルに指示する際、エラーや手戻りのないスムーズな開発が可能になります。

## 疑問・課題点 1：ブラウザ検索システムの「クリック可能な単語」の実装方法（★A案に決定）
### 【AIが疑問に思うポイント】
> 「見た目に違いのない普通のワードと検索可能ワード」を、プログラムでどう識別・管理するのか？

- **課題詳細**:
  ゲーム内のテキスト（SNSやニュース記事など）から、プレイヤーに任意の単語をクリックさせますが、すべてのテキスト（一文字単位、あるいは助詞なども含むすべて）をクリック可能にする（形態素解析などを使う）のか、それとも**「あらかじめ開発者が仕込んだ、クリック可能な名詞リスト」**だけをクリックできるようにするのか。
- **実装上の影響**:
  - もし「あらかじめ仕込んだ単語」だけをクリック可能にする場合、マウスカーソルが重なった時（ホバー時）にカーソルの形が変わったりすると、「ここがクリックできる」というヒントになってしまい、**「見た目の違いはない（ノーヒント）」という仕様と矛盾**してしまいます。
- **決定した解決案（プログラミング指示）**:
  - **A案を採用**: テキスト（WebページやSNS、会話ログ）全体を、内部的には「あらかじめ定義したキーワード/通常単語」単位でスパン分割（`<span>`タグなど）して配置し、クリックイベントを付与します。
  - **ホバー表示の完全無効化**: CSS等で、ホバー時のマウスカーソル（ポインター）変化、色変更、アンダーライン表示などのホバーエフェクトを完全に無効化します。これにより、プレイヤーは画面を適当にホバーしても「どこがクリックできるキーなのか」を判断できず、自らの論理的推測だけで単語をクリックすることになります。

## 疑問・課題点 2：特定の2つの証拠が揃った時の「トリガー判定」の仕組み（★決定）
### 【AIが疑問に思うポイント】
> 証拠が揃って会話が発生するトリガーは、どのようなデータ構造で管理されるのか？

- **課題詳細**:
  「特定の2つ以上の証拠が獲得された瞬間」に、会話イベントを発生させてボードを更新する処理が必要です。これをコード内にハードコーディングすると、シナリオの追加や修正が難しくなります。
- **決定した解決案（プログラミング指示）**:
  - 以下のJSONデータ構造でイベントおよび相関関係を管理する仕組みを決定しました。実装時はこのデータ（配列）を読み込んで、証拠獲得の都度、条件に合うトリガーがないかを監視（リアクティブに判定）するロジックを組んでください。
  ```json
  {
    "trigger_id": "ch1_evidence_match_1",
    "required_evidences": ["evidence_ch1_A", "evidence_ch1_B"],
    "event_flow": "conversation_ch1_match_1",
    "board_update": {
      "draw_line": {
        "from": "evidence_ch1_A",
        "to": "evidence_ch1_B",
        "relation_type": "contradiction",
        "label": "矛盾"
      }
    }
  }
  ```

## 疑問・課題点 3：推理パートにおける「矛盾指摘」の具体的なUIと操作手順（★決定）
### 【AIが疑問に思うポイント】
> 「相手の発言の矛盾する部分を選択し、証拠を突きつける」とは、具体的にどんなUI操作なのか？

- **課題詳細**:
  「相手の発言の矛盾する部分を選択する」という操作が、文字通り「相手のセリフテキストの特定の1行（あるいは特定の単語）をクリックする」ことなのか、それとも「相手の主張が選択肢として画面に3つほど並び、その選択肢を選ぶ」ことなのか。
- **決定した解決案（プログラミング指示）**:
  - 実装が最も安定し、中高生にとっても直感的である**「2ステップUI案」**を採用します。
  - **手順**:
    1. 相手が1〜3つの文（主張）を提示します。それぞれが選択可能なテキストボックス（バブル）として表現されます。
    2. プレイヤーは「矛盾している」と思う相手の発言ボックスを選択状態（枠線が強調される等）にします。
    3. その後、画面下部に並ぶ「所持している証拠付箋一覧」から、矛盾を暴く付箋を1つ選択。
    4. 「突きつける」ボタンを押すと、判定ロジックが走り、正誤の演出が実行されます。

## 疑問・課題点 4：ライフが「2」になった際のアシストタイミングと演出（★決定）
### 【AIが疑問に思うポイント】
> アオイがヒントをくれるタイミングは、「間違えた直後」なのか、それとも「次の解答中」なのか？

- **課題詳細**:
  ライフが2になった（1回間違えた）際のアシスト会話は、どのタイミングで挿入されるのがプレイヤーにとって最も自然か。
- **決定した解決案（プログラミング指示）**:
  - プレイヤーへの配慮と体験（不快感の軽減）を考慮し、以下のフローを決定しました。
  - **詳細フロー**:
    1. プレイヤーが間違った組み合わせを提示すると、不正解を示す画面演出（大きく赤いバツ等）が表示され、不快感のない適切な警告音（SE）が流れます。
    2. その後、推理画面からアオイの立ち絵がある「会話画面」へと、一度完全に切り替わります。
    3. アオイは「焦り」を表現するのではなく、レンを優しく導くように**「柔らかいアドバイス調」**で語りかけます。
       - **台詞例**:「レン、焦らなくて大丈夫だよ。一度落ち着いてみよう。相手のさっきの発言、私たちが集めたあの証拠と食い違っているところがないか、もう一度よく見比べてみて？」
    4. 会話終了後、再度推理画面へとスムーズに戻り、解答を再開できるようにします。
  - これにより、プレイヤーは失敗しても「叱られた」「ゲームオーバーに近づいた」というストレスを感じにくく、安心して次の考察に進むことができます。

## 疑問・課題点 5：表示テキストを管理しているファイルと設計方針について
### 【AIや開発者が疑問に思うポイント】
> Q: ゲーム内のシナリオセリフやWebページの表示テキストは、現在どのファイルで管理されていますか？また、今後の本開発における設計はどうすべきですか？

- **現在のデモ実装における配置**:
  - デモ用の動作確認プログラムでは、実装のシンプルさを重視し、オープニング会話、SNSタイムライン、検索エンジンの検索結果、デマ論破の主張、証拠付箋、エピローグのすべての表示テキストを **`/src/App.tsx`** 内に定数配列やオブジェクトとしてハードコード（直接記述）して管理しています。
- **今後の本開発（完成版ゲーム）における設計方針**:
  - 本開発のフェーズでは、テキストの誤字脱字修正やシナリオの追加・変更、多言語対応（ローカライズ）の保守性を向上させるため、表示テキストをプログラムコードから完全に切り離すことを強く推奨します。
  - 具体的には、**各チャプターごとのシナリオJSONデータファイル（例: `/src/data/chapter1.json`）**として外部に切り出し、プログラム実行時に動的に読み込む設計（データ駆動型設計）に移行します。これにより、ノンプログラマーのシナリオライターでもコードを破壊することなく安全にテキストの追加・修正が可能になります。
